# Agent 重建复盘与 VLM、数据引擎协同计划

日期：2026-09-21  
状态：复盘与开发计划，不包含代码修改

## 1. 结论

这次不经过 Parser，Agent 直接观察 8 张多源几何图和题目文本，人工建立 construction trace、Geometry State 并重画，最终 8/8 trace 可执行、8/8 通过严格验证。

真正有效的过程不是“从像素恢复完整精确坐标”，而是：

```text
理解题图整体结构
    -> 注册对象与稳定 ID
    -> 建立拓扑和对象引用
    -> 提取数学关系、数量和 target
    -> 区分确定事实、布局观察和不确定线索
    -> 求一组满足约束的合法 realization
    -> 编译为 Geometry State
    -> verifier 检查
    -> renderer 重画
```

因此，后续自动化目标不应是让 VLM 直接生成最终坐标或 Geosym 构造脚本，而应让 VLM 尽量复现 Agent 的“结构理解”阶段，再由确定性模块完成引用检查、约束实现、验证和渲染。

## 2. Agent 实际如何完成重建

### 2.1 先理解整张图，不逐像素追线

Agent 首先判断题图属于什么结构，例如：

- 一个三角形及三条中线；
- 一个圆、一条弦和过圆心的垂线；
- 一个长方形及外接垂直线；
- 一个四分之一圆和内切圆；
- 一个带高、对角线和阴影的多边形。

这个整体判断决定哪些线是主体边、内部构造、延长线或纯显示元素。若没有这一步，局部线段检测会产生大量互相割裂的候选。

### 2.2 先建立对象注册表，再写关系

Agent 先确定点、线段、圆、弧、多边形和区域，再让所有关系引用这些稳定对象。例如：

```text
points: J, K, L, R, S, T, P
segments: JK, KL, JL, JS, KT, LR
topology: R on JK, S on KL, T on JL
relations: R/S/T are midpoints; JS/KT/LR concur at P
```

这避免了当前自动流程中常见的“关系已经提到 ST，但 ST 没有定义”“点名存在，但绑定到错误边”问题。

### 2.3 拓扑优先于长度和坐标

Agent 先确定：

- 哪些点在同一条边上；
- 哪些线相交；
- 多边形边界按什么顺序连接；
- 哪个点是垂足、中点或圆心；
- 哪条线是主体边、辅助线或延长线。

只有拓扑稳定后，才加入垂直、平行、等长、数值和 target。绝大多数“重画完全无关”的失败，本质上是对象引用或拓扑在前面已经断裂，不是 renderer 不会画。

### 2.4 将三种信息严格分开

本次重建中使用了三类信息：

1. **数学不变量**：共线、垂直、平行、中点、等长、相切、点在线上、边界顺序等。
2. **布局观察**：点的大致上下左右、线的粗略方向、对象相对位置，只用于选择一个接近原图的 realization。
3. **显示标注**：点名、数值、刻线、直角符号、填充、虚线和颜色，只决定如何展示，不自动升级为数学事实。

原图中可见但数学角色不确定的虚线被保留为辅助对象，但没有擅自声明 theorem relation。原图未标名的支撑点具有内部稳定 ID，但不会显示名称。

### 2.5 不恢复像素坐标，而是求合法坐标

证明题的图通常不按比例，像素位置也不是数学真值。Agent 根据已确认约束构造一组合法坐标：

- 中点和交点使用精确有理坐标；
- 垂足通过正交投影构造；
- 内切圆使用根式半径；
- 长方形、菱形和面积分割直接满足其定义约束；
- 只有相对朝向参考原图。

首轮曾使用浮点投影，严格 verifier 正确地拒绝了近似垂直。改为有理数和根式后通过。这说明坐标 witness 必须明确区分精确值与容差数值值。

### 2.6 Geometry State 是唯一正式结果

所有数学对象先进入 construction trace 和 Geometry State。颜色、透明度、虚线以及少量显示刻线只在 renderer-neutral scene 层调整。最终是否成功由 state/trace verifier 判断，而不是由“图片看起来像”判断。

## 3. 对当前自动流程的启示

### 3.1 VLM 已经适合承担结构理解，但不应承担全部工作

VLM 应负责：

- 概括整图结构；
- 枚举可见对象；
- 绑定点名、线名、数值和符号；
- 输出拓扑、关系和 target 候选；
- 标明证据来源、置信度和歧义分支；
- 给出粗略相对布局。

VLM 不应负责：

- 直接生成最终 Geometry State；
- 猜测满足约束的精确坐标；
- 输出引擎内部 construction op；
- 自己宣布关系已通过 verifier；
- 为迎合 builder 而省略暂不支持的对象；
- 把不确定辅助线强行解释为定理条件。

### 3.2 OpenCV 和 OCR 只能提供证据，不能支配语义

OCR 的合理职责是提供文本内容、候选框和字符置信度；OpenCV 的合理职责是提供局部线、圆、弧、交点、虚实线和 marker 候选。它们可以帮助定位和校验，但不能因为局部像素不理想就否决 VLM 已正确识别的全局拓扑。

建议默认策略：

- VLM 负责对象身份和全局关系；
- OCR/OpenCV 提供可绑定的 observation；
- 只有证据充分的严重矛盾才触发拒绝；
- 证据不足时标记 `unverified`，不等于 `false`；
- image-only 模式允许没有 OCR 文本绑定，image+text 模式单独计量收益。

## 4. 新的最小数据协议

VLM 每张图只输出一份紧凑的 `DiagramProposal`，不输出构造脚本。建议字段如下：

```text
diagram_summary
objects
  points
  segments / lines / rays
  circles / arcs
  polygons / regions
topology
  incidence
  ordered_points
  boundary_cycles
  intersections
relations
quantities
target
layout_hints
display_annotations
ambiguities
```

具体约束：

- 所有对象先定义后引用；
- 对象使用本次响应内稳定 ID，显示名称另设字段；
- `segment(P,Q)` 与视觉线条 ID 分开，不能依赖字符串拆点名；
- relation 必须引用已定义对象；
- quantity 必须绑定对象或角，而不是只返回裸字符串；
- `layout_hints` 只保存归一化锚点、方向和相对位置，不是精确数学坐标；
- `display_annotations` 保存刻线组、箭头组、直角框、虚线、阴影和可见文本；
- 无法确定时返回候选分支和原因，不允许默默删掉对象。

提示词保持通用，只解释上述协议和判断原则，不加入 Geometry3K、GeoQA 等数据集特例，也不要求模型输出 builder capability、修复动作或内部审计字段。

## 5. VLM 到 Geometry State 的主流程

```text
image + optional question
    -> VLM DiagramProposal
    -> ReferenceValidator
    -> SemanticNormalizer
    -> EvidenceBinder（可选 OCR/OpenCV）
    -> Admission
    -> ConstraintGraph
    -> RealizationClassifier
         |-> exact realization
         |-> constrained seed realization
         `-> seed completion with explicit assumptions
    -> ConstructionCompiler
    -> Geometry State
    -> TraceVerifier / StateVerifier
    -> Renderer
```

### 5.1 ReferenceValidator

只做确定性检查：重复 ID、悬空引用、类型不匹配、边界不闭合、点名冲突、数量未绑定。失败必须返回精确路径，不做静默修补。

### 5.2 SemanticNormalizer

统一同义关系和引用形式，例如 `lies_on`、`on_segment`、`between`、`collinear`；必要时从已定义端点补出显式 segment，但必须记录这是编译派生对象。

### 5.3 EvidenceBinder

把 VLM 语义对象绑定到 OCR/OpenCV observation。绑定成功提高证据等级；未绑定不直接删除语义对象。像素检查主要用于发现明显的点线身份错配，而不是要求不按比例的题图满足精确角度和长度。

### 5.4 Admission

分别决定 object、topology、relation、quantity、target 是否进入 admitted graph。VLM confidence 只是输入证据之一，不能替代规则验证。

### 5.5 RealizationClassifier

正式区分三种结果：

1. `exact`：文本和约束足以确定可严格验证的状态；
2. `constraint_seed`：结构明确但存在自由度，生成一组满足约束的合法 seed；
3. `completed_seed`：为合成用途显式采样缺失参数或加入假设，不宣称恢复原题。

“不能唯一恢复坐标”不再等于“不能重建”。只有引用冲突、约束矛盾或关键拓扑缺失才应阻止 seed realization。

### 5.6 ConstructionCompiler

只保留一份通用对象/关系到 ConstructionOp 的编译实现。不同 realization 策略只决定坐标 witness、分支和新增假设，不各自复制一套 builder。

## 6. 数据引擎如何配合

### 6.1 合成数据提供监督，不向 Parser 泄漏答案

合成引擎已有完整 state、trace、scene 和 lineage。应导出两套严格隔离的数据：

- public input：图片与可选题目文本；
- private reference：DiagramProposal 真值、Geometry State、显示标注、拓扑、关系、数量、target 和 lineage。

VLM 只能读取 public input；评测器使用 private reference 逐组件对比。

### 6.2 由正式 state 自动生成 VLM 协议真值

数据引擎需要一个单向导出器：

```text
Geometry State + RenderScene
    -> reference DiagramProposal
```

对象和数学关系来自 state；刻线、虚线、颜色、标签可见性来自 scene。这样可以训练和评测“数学结构”与“显示证据”两个层次，避免把 renderer metadata 当 Parser 输入。

### 6.3 Parsed seed 反向进入受控合成

经过 verifier 的 `constraint_seed` 可以进入合成引擎作为 base spec：

- 固定原图恢复出的拓扑和 admitted constraints；
- 对自由参数进行有记录的采样；
- 增加目标驱动的构造和 derivation；
- 生成多种合法布局、样式和题目；
- lineage 明确标记 `source_recovered` 与 `synthetic_completion` 的边界。

这样真实图片不必被完整求解，也能提供结构分布；同时任何新增长度、坐标或辅助构造都不会被误称为原题事实。

### 6.4 用失败类型驱动合成课程

自动评测的失败切片应反向控制合成采样，例如：

- 对象漏检：增加密集标签、短边、孤立辅助点；
- incidence 错误：增加边上点、交点、共线链；
- marker 绑定错误：增加多组刻线、平行箭头和多个直角；
- quantity 绑定错误：增加相邻数值、根式、分式、单位；
- circle/arc 错误：增加弦、切线、扇形、相交圆；
- region 错误：增加阴影、多组件和孔洞。

训练集、开发集和测试集仍按 base structure 隔离，不能让同一 state 的样式变体跨 split。

## 7. 评测口径

不再用单一的“成功/失败”覆盖所有阶段。至少分别报告：

- object inventory precision/recall；
- stable-name binding accuracy；
- segment endpoint accuracy；
- incidence 和 ordered-points F1；
- relation F1；
- quantity extraction 与 object-binding accuracy；
- target accuracy；
- unresolved reference rate；
- admitted graph coverage；
- exact realization rate；
- constraint-seed realization rate；
- state verifier pass rate；
- semantic redraw topology score；
- completed-seed assumption count。

人工审阅必须区分：完整恢复、可用结构种子、部分结构、不可用。生成了图片不能单独算成功。

## 8. 分阶段开发计划

### 阶段一：冻结协议与人工基线

- 将本次 8 张人工重建整理为只读 gold fixtures；
- 为每张图补齐 reference `DiagramProposal`；
- 冻结对象、拓扑、关系、数量、显示标注和歧义字段；
- 建立协议级 schema 测试，不涉及模型和像素算法。

验收：8 个 proposal 均可无人工修补地编译到现有人工 trace，引用完整率 100%。

### 阶段二：重写紧凑 VLM 提取脚本

- 每图一次结构提取请求；
- 输出唯一 `DiagramProposal`；
- image-only 和 image+text 使用同一协议；
- provider 仅负责传输和 JSON 解码；
- 不做重试、repair chain、builder 指令生成和测试集特化。

验收：模型输出可解析率、引用完整率和字段覆盖分别统计；错误不能被静默吞掉。

### 阶段三：实现确定性编译与分级准入

- 完成 ReferenceValidator 和 SemanticNormalizer；
- 将 OCR/OpenCV 改为可选 EvidenceBinder；
- 对 object、topology、relation、quantity 分别准入；
- 保留所有 rejected/abstained 候选及原因。

验收：不再出现“VLM 已输出对象，但合并阶段丢失”“关系引用未定义伪线段后整图消失”。

### 阶段四：完成通用 2D SeedRealizer

优先支持：

- 点、线段、射线、直线、多边形；
- 点在线上、共线、between、交点；
- 平行、垂直、中点、比例点、等长；
- 三角形、四边形、矩形、菱形；
- 自由度保留和合法布局采样。

验收：本次线性 2D 人工样本可以仅由 proposal 自动生成合法 seed，且 verifier 通过。

### 阶段五：圆、弧与区域 realization

- 圆心、半径、圆上点、弦、切线；
- 圆弧、扇形、四分之一圆和相交圆；
- polygon region、阴影、区域分割和孔洞；
- 相切、边界闭合和区域合法性验证。

验收：四分之一圆内切圆、圆弦垂线和面积图无需专用 case builder。

### 阶段六：建立数据引擎闭环

- state/scene 自动导出 reference proposal；
- synthetic clean、perturbation 和真实图统一使用同一评测协议；
- verified parsed seed 可进入受控合成；
- 失败切片驱动下一轮合成分布；
- 结果目录只保留 summary、records、images/review 和按需 debug。

验收：100 张多源图片能够按统一口径给出逐阶段指标，并能明确区分 exact、constraint seed、completed seed 和 unsupported。

## 9. 开发规则

1. 不为单张失败图片增加专用模板、ID 修复或 prompt 分支。
2. 新能力必须用“对象类型或约束类型”定义，而不是用数据集名称定义。
3. VLM 输出、evidence、admission、realization 和 Geometry State 各只有一个正式数据模型。
4. 每个阶段只能消费上一阶段的正式输出，不旁路读取旧中间文件。
5. 不确定信息保留为 hypothesis；未验证不等于错误，未实现不等于原图不存在。
6. seed completion 新增的每个假设必须可追溯，不能写回 source fact。
7. renderer 只消费 Geometry State 和显示策略，不参与补几何语义。
8. 首先保证 reference integrity、拓扑和 verifier，再优化视觉相似度。
9. artifacts 默认采用紧凑目录；详细模型响应和 evidence 只在 debug 级别保存。
10. 每扩展一类能力，至少覆盖合成 clean、合成扰动和多个真实来源，不以单一 benchmark 通过作为完成标准。

## 10. 最终目标

最终主链应足够短：

```text
VLM 看懂并描述
    -> 确定性模块检查并组织
    -> 几何引擎寻找合法实现
    -> verifier 决定可信级别
    -> renderer 重画
    -> 数据引擎把可信 seed 扩展为可追溯数据
```

其中 VLM 像人一样负责“看懂和提出结构”，Geosym-World 负责“形式化、实现、验证和生成”。二者通过一个稳定、通用、紧凑的语义协议配合，而不是通过不断增长的 repair pipeline 配合。
