## 1. 结论摘要

我对目标的理解不是“把当前大目录拆成两个名字更清楚的项目”，而是要重新建立两个职责明确、接口稳定、可以独立演进的系统：

1. **Geosym-World** 是几何数据与几何计算基座。它统一承载 2D/3D 几何状态、构造、求解、验证、渲染、合成、Parser、数据适配、Benchmark、Eval 和 Diagnosis。
2. **GeoClaw** 是建立在该基座上的 verifier-gated 几何 Agent 系统。它负责模型接入、动作协议、工具调度、事务执行、状态提交/回滚、反馈投影、轨迹记录、重放和 Agent 评测。
3. 两个仓库之间必须保持单向依赖：`GeoClaw -> Geosym-World`。Geosym-World 不得导入 GeoClaw，GeoClaw 不再复制一份几何内核。
4. 两者共享的核心不是一批零散 helper，而是一个有版本的 **Geometry State Contract**：稳定对象 ID、typed primitives、约束、假设、事实、来源、构造历史、目标、视觉 grounding 和验证结果。
5. Parser 的输出不能直接升级为事实。Parser 产生的是带置信度和证据来源的 hypothesis；只有通过几何验证、工具检查或明确的 admission 规则后，才能进入持久事实状态。
6. 清理的目标是把旧实验、半成品、重复实现和生成产物移出活动代码树，但不能在能力迁移和回归验证之前直接删除。有效测试应迁移为新契约的保护网；应删除的是失效测试、一次性 smoke 脚本、测试结果和无主代码。
7. 两个项目都采用递进开发，不把长期研究目标当作首期交付。优先完成输入确定、可自动验证、可建立回归基线的能力；真实图解析、不确定状态推理和高级 3D 等高风险能力在前置指标稳定后再进入主线。

## 2. 我对两个项目的产品理解

### 2.1 Geosym-World：几何数据基座

Geosym-World 不应只被定义为“合成数据生成器”。它的长期定位是统一的 geometry data operating layer，服务数据生成、几何工具、组件评测、上层 Agent，并逐步扩展到真实数据解析。这里的“真实数据解析”是独立的高风险研究方向，不是仓库重构后立即能够稳定交付的能力。

长期希望形成以下闭环，但实现顺序必须从结构化真值和合成数据开始，再逐步进入真实题图：

```text
结构化记录 / 合成真值 ----------------------+
                                          |
真实题图 / 文本 / 标注 / CAD -- Parser --+-> Geometry Hypotheses
                                                  |
                                                  v
                                      Grounding / Verification
                                                  |
                                                  v
                                      Canonical Geometry State
                                                  |
                  +-------------------------------+--------------------+
                  |               |               |                    |
               Solver          Renderer        Dataset             GeoClaw
            Construction      Annotation      Benchmark           Environment
               Tools         Visualization   Eval/Diagnosis
```

Geosym-World 的长期能力范围包括：

- 统一的 2D/3D typed geometry schema；
- 精确值与数值值并存的几何内核；
- 构造轨迹执行、约束检查和事实闭包；
- 2D/3D 合成、扰动、增强、标注和批量生成；
- 图片、文本、已有标注到统一状态的 Parser；
- 数据集注册、格式适配、版本、lineage 和 manifest；
- Parser、内核、合成、渲染及数据质量的 Benchmark；
- 可复用的构造、测量、计算、验证、渲染等领域工具；
- 面向失败组件、错误类型和数据切片的 Eval/Diagnosis。

“数据支持更广”不应只意味着多读几种 JSON，而应意味着不同来源最终进入同一个可验证状态模型，并保留来源差异：原图、OCR、文本条件、人工标注、合成真值、模型假设、求解器推导和 Agent 构造不能混成同一种事实。

### 2.2 GeoClaw：Verifier-Gated Geometry Agents

GeoClaw 的主体不是另一个几何引擎，也不是单纯的 prompt runner。它应是一个把模型决策限制在可验证状态转换中的 Agent runtime。

核心闭环应为：

```text
Public Problem + Current Observation
               |
               v
         Model / Controller
               |
               v
          Typed Action
               |
               v
Schema Gate -> Policy Gate -> Grounding Gate
               |
               v
      Tentative Tool Execution
               |
               v
 Geometry / Tool Verifier Gate
          | accepted      | rejected
          v               v
     Commit State      Rollback
          |               |
          +-------> Typed Public Feedback
                         |
                         v
                  Next Agent Step
```

GeoClaw 需要重点拥有：

- 多模型、多供应商的 model adapter；
- controller、planner、policy 和 budget 管理；
- typed action/observation/feedback 协议；
- 可提交或回滚的事务式环境；
- schema、policy、privacy、budget、tool-specific 和 geometry gate 的组合；
- Agent 使用的工具包装和权限配置；
- accepted/rejected action 的持久轨迹、checkpoint、rollback 和 replay；
- 最终答案、过程质量、工具使用、错误恢复、成本和轨迹的评测；
- 面向模型、任务、工具、错误类型和策略的实验配置与诊断。

GeoClaw 可以调用 Geosym-World 的工具，但 Agent 语义属于 GeoClaw。例如，“作一条过点 A 的垂线”的几何执行与验证属于 Geosym-World；该动作是否对当前 Agent 开放、是否超预算、是否泄漏 oracle、失败后向模型公开哪些信息，属于 GeoClaw。

### 2.3 递进开发原则

两个项目统一采用三层路线：

1. **已经有的**：当前代码中能够找到实现、原型、测试或实验记录的能力。它们是迁移候选，不等于已经达到生产质量。
2. **首先开发的**：输入边界清楚、可确定性验证、主要依赖已经存在，重构后最可能形成稳定版本的能力。
3. **其次开发的**：研究难度更高，或依赖前一阶段的数据、指标、状态契约和 Agent 闭环。它们只有在前置 gate 达标后才进入主线。

不以目录创建或 API 占位表示某项能力“已完成”。每一层都要有可执行 fixture、指标和退出条件。

### 2.4 Geosym-World 递进路线

#### 已经有的

- 形式几何状态、构造轨迹、对象 ID、FactStore、solver 和 verifier 的实现基础；
- 点、线、射线、线段、圆、弧、多边形、区域、平面、多面体等 2D/3D 对象候选；
- SVG/PNG 渲染、scene、样式策略、角标、垂足、延长线、表达式和标签布局能力；
- 模板驱动的 2D 合成、增强、去重、exact-count、QA/GT 和 manifest 管线；
- `geosym3d` 中两代 3D 原型，其中 `geosymsolid` 具备 SymPy、CAD 验证、渲染和 QA 候选能力；
- 根 `geosym` 中的 Parser、canonical schema、answer grader、Eval 和 Diagnosis 原型；
- 真实图片解析的尝试和运行记录，但目前不能视为稳定、通用或已达到明确准确率门槛的能力。

#### 首先开发的：确定性数据基座

目标是先让“已知形式状态或可控合成输入”完整、稳定、可复现，不把真实图片 Parser 作为阻塞项。

1. 冻结 Geometry State Contract v1，统一 ID、实体、关系、quantity、target、trace、fact、provenance 和 serialization；
2. 合并并稳定 2D 内核、construction、solver、verifier，建立 exact-state 回归；
3. 迁移基础 3D primitive 和最小验证链，只承诺当前可验证的实体、关系和截面能力；
4. 稳定 SVG/PNG 同 scene 渲染及几何标注 QA；
5. 稳定合成流水线、数据 record、lineage、manifest、exact-count 和进度报告；
6. 建立数据 adapter/registry 的最小版本，优先支持结构化标注和当前已有数据格式；
7. 建立组件 Benchmark 骨架，先覆盖 schema、kernel、solver、verifier、rendering 和 synthesis；
8. 实现 Parser v0：只处理合成图、矢量图、干净标准图和结构化文本，并输出 hypothesis，不宣称开放世界真实题图能力。

首期退出条件：同一 record 能稳定完成 `build -> solve -> verify -> render -> serialize -> reload`；合成和 Parser v0 有可重复指标；旧能力迁移有 parity 证据。

#### 其次开发的：真实解析与复杂几何

真实数据解析按难度分层推进，不能直接用一个“real parser”任务概括：

1. 合成 raster 和矢量图的对象、关系、文字、target 联合解析；
2. 版式相对统一的公开几何数据集，建立人工对齐的小规模 gold set；
3. 扫描、压缩、遮挡、低分辨率、符号歧义和标签冲突下的鲁棒解析；
4. 图像与题干文本融合、候选关系排序、冲突消解和 hypothesis admission；
5. 跨数据集泛化、校准、拒识和人工修订接口；
6. 更复杂的合成 grammar、迭代构造、证明程序、阴影区域和多步骤 target；
7. 高级 3D 构造、截切、投影、展开、CAD 一致性和 3D Parser。

进入条件：Parser v0 的分组件指标稳定，错误能够归因到 detection/OCR/fusion/grounding/schema，且 benchmark 能区分“没有识别到”和“识别后几何不一致”。

### 2.5 GeoClaw 递进路线

#### 已经有的

- typed action、observation、feedback 和 evidence level 的协议基础；
- `GeoClawEnvironment`、工具注册、step budget、状态观察和 trajectory；
- construct 的 tentative execution、验证后提交、失败回滚语义；
- zoom、calculate、measure、construct、verify、final 等工具原型；
- public/private payload 分离、privacy projection 和工具策略；
- scripted client、OpenAI-compatible model client、Direct/Open-loop/Closed-loop runner；
- frozen task、实验结果和回放中的闭环验证基线。

#### 首先开发的：基于确定性状态的 Agent Runtime

首期 GeoClaw 不依赖真实图片 Parser。它先消费 Geosym-World 提供的可信 formal task、public problem 和渲染图，验证 Agent runtime 本身是否正确。

1. 将 GeoClaw 从复制的几何包中解耦，严格依赖 Geosym-World；
2. 冻结 action/observation/feedback 和 tool capability contract；
3. 明确 persistent state、tentative state、commit、rollback 和 state version；
4. 组合 schema、policy、grounding、budget、privacy、tool 和 geometry gates；
5. 稳定模型 provider 接口，先支持 scripted client 和一个 OpenAI-compatible 路径；
6. 稳定 construct/calculate/verify/render/inspect 等最小工具集；
7. 实现可校验的 trajectory ledger、checkpoint、replay 和 typed failure；
8. 在合成 2D 任务上建立 final accuracy、action validity、recovery、token、latency 和 cost 指标。

首期退出条件：无效动作不改变持久状态；同一轨迹 replay 得到相同状态 checksum；公开 payload 无私有真值泄漏；至少一个模型接入可以在固定任务集上完整运行。

#### 其次开发的：不确定感知与真实题图 Agent

1. 消费 Geosym-World Parser 输出的多候选 hypothesis，而不是假设初始状态完全正确；
2. 让 Agent 能检查、比较、拒绝或请求补充证据，再由 gate 决定是否 admission；
3. 增加面向 OCR、grounding、关系冲突和构造失败的恢复策略；
4. 在真实题图上联合评测 Parser 错误、Agent 决策错误和工具执行错误；
5. 扩展到复杂多步证明、长程规划、动态工具选择和预算优化；
6. 在 Geosym-World 3D 状态和工具稳定后，再加入 3D geometry Agent；
7. 扩展多模型、多 provider、策略消融和跨数据集诊断。

进入条件：Geosym-World 能稳定输出带 confidence/provenance 的 hypotheses，GeoClaw 首期 runtime 已通过 rollback、replay、privacy 和 formal-task 基线。

### 2.6 两个项目的依赖 gate

| 前置能力 | 可以启动的后续能力 |
|---|---|
| Geometry State Contract v1 | 2D/3D 内核迁移、Parser 输出、GeoClaw state/action contract |
| 稳定 2D kernel + verifier + tools | GeoClaw 2D formal-task 闭环 |
| 稳定 synthesis + rendering + record | Parser v0、合成 Benchmark、GeoClaw 可控任务集 |
| Parser v0 + 分组件指标 | 标准化真实数据 Parser 研究 |
| calibrated hypotheses + provenance | GeoClaw 不确定状态 admission 和恢复 |
| 稳定 3D kernel + renderer + tools | 3D synthesis、3D benchmark、GeoClaw 3D Agent |

真实 Parser 失败不会阻塞首期 GeoClaw；高级 GeoClaw 也不能反过来要求 Parser 直接伪造完整正确状态。

## 3. 重构前工作区的事实基线

### 3.1 当前 Git 结构

当前可识别的有效 Git 仓库有两个，但位置不符合目标：

```text
/data/Geosym127K/geosym_world_geometry/.git
/data/Geosym127K/geosym_world_geometry/GeoClaw/.git
```

`/data/Geosym127K/.git` 目前不是有效仓库，应视为无效残留，后续经确认后删除。目标结构中工作区根目录不应是第三个 Git 仓库。

当前外层 `geosym_world_geometry` 工作树非常脏：约有 1006 个删除、22 个修改和 7 个未跟踪项。大量删除来自曾被跟踪的生成图片。这些状态不能通过一次 `git add -A` 或强制 reset 粗暴处理，必须先确认用户改动和产物处置。

当前内层 GeoClaw 仓库有未跟踪的 `REPOSITORY_REFACTOR_SUMMARY.md`。它属于并行工作痕迹，重构前必须纳入清单，不能覆盖或误删。

### 3.2 当前代码和资产混杂

工作区主要体积包括：

| 路径 | 约占用 | 当前判断 |
|---|---:|---|
| `datas/` | 1.1 GB | 数据、回放批次、smoke 和中间结果混合 |
| `geosym_world_geometry/` | 333 MB | 内核、合成、Agent、论文、输出、嵌套仓库混合 |
| `output/` | 95 MB | 3D 渲染和调试输出 |
| `geosym/` | 2.2 MB | Parser、统一 schema、Eval、Diagnosis 的候选来源 |
| `scripts/` | 1.5 MB | 旧 2D 工具链和兼容来源 |
| `geosym3d/` | 600 KB | 两代 3D 实现混合 |

外层几何实现有 92 个 Python 文件，内层 GeoClaw 复制的几何包有 91 个 Python 文件，其中 73 个相对路径相同。即使文件内容已经分叉，这也足以说明当前存在严重的源码复制和双向漂移风险。

### 3.3 当前能力不能一概删除

现有代码中至少有四类有价值资产：

1. 外层 `geosym_world_geometry` 的形式状态、构造、事实、solver、verifier、渲染和合成管线；
2. 根目录 `geosym` 中的 canonical state、真实图片 Parser、answer grader、Eval 和 Diagnosis 思路；
3. `geosym3d/geosymsolid` 中基于 SymPy、CadQuery/OpenCascade、渲染和 QA 的 3D 新实现；
4. 内层 GeoClaw 中的 action protocol、环境事务、模型适配、privacy projection、runner、trajectory 和实验契约。

因此，“精简”应以职责和能力为标准，不应以“旧目录”或“测试文件”作为唯一删除依据。

## 4. 目标工作区

建议最终工作区结构如下：

```text
/data/Geosym127K/
├── AGENTS.md                  # 工作区级规则，只描述跨仓约束
├── Geosym-World/              # 独立 Git 仓库，自有 artifacts/
├── GeoClaw/                   # 独立 Git 仓库，自有 artifacts/
├── archive/                  # 非活动的只读历史快照
├── docs/                     # 工作区迁移记录和面向用户的报告
│   ├── internal/
│   └── reports/
└── tmp/                      # 一次性脚本和临时调试产物
```

目标约束：

- 工作区内活动 Git 根只有 `Geosym-World` 和 `GeoClaw`；
- 每个仓库在自己的根目录维护 `artifacts/`，不再使用工作区共享 artifacts；
- 两个 `artifacts/` 默认由各自 `.gitignore` 排除，只允许跟踪 schema、README 或极小 fixture；
- 工作区 `archive/`、`docs/` 和 `tmp/` 不是第三个代码仓库；
- 两个仓库都可独立安装、测试和发布；
- 数据和生成结果默认不进入源码仓库；
- 两个仓库各有自己的 `AGENTS.md`，工作区 `AGENTS.md` 只约束跨仓行为。

### 5.1 内部依赖方向

```text
schema
  ^
  +-- kernel / construction
  +-- parser
  +-- datasets

kernel + construction
  -> solver -> verifier
  -> rendering
  -> synthesis
  -> tools

schema + parser + synthesis + datasets
  -> benchmark/eval/diagnosis
```

Parser、synthesis 和 benchmark 不应分别定义自己的点、线、事实和 target schema。它们只能使用 `schema/` 中的同一版本契约。

### 5.2 2D 和 3D 的关系

2D 和 3D 不应被做成两个互不兼容的世界，也不应强行塞进一个巨型对象类。建议共享：

- stable ID；
- entity/fact/hypothesis/provenance 接口；
- quantity 和 exact value 表达；
- construction trace；
- target 和 verification report；
- dataset record 和 lineage。

维度相关的坐标、相交、拓扑、退化检查、CAD 验证和渲染实现分别留在 `geometry2d/` 与 `geometry3d/`。平面截多面体、投影、展开图等跨维任务通过明确的 mapping/projection record 连接，不能靠隐式字段猜测。

## 7. 两仓共享契约

### 7.1 Canonical Geometry State

建议新契约至少明确以下层次：

| 层次 | 内容 | 是否可直接作为事实 |
|---|---|---:|
| Source | 原图、文本、数据集记录、CAD、生成配置 | 否 |
| Observation | 检测框、像素点、OCR、视觉关系 | 否 |
| Hypothesis | Parser 提议的对象、关系、数值及置信度 | 否 |
| Admitted Entity/Constraint | 经规则或验证接纳的对象与约束 | 是 |
| Derived Fact | Solver/Verifier 推导的事实和依赖 | 是 |
| Construction Event | 用户、生成器或 Agent 提交的构造动作 | 接纳后改变状态 |
| Target | 待求量、待证关系、构造目标或区域目标 | 不是事实 |
| Certificate | 私有真值、推导链、数值证书、评测信息 | 私有 |

每个事实或假设至少携带：

- 稳定 ID 和 schema version；
- 类型和参数；
- exact value、numeric approximation 及容差策略；
- source/provenance；
- dependencies；
- confidence 或 admission status；
- public/private visibility；
- 创建或接纳它的 event ID。

这能防止当前研究摘要中最关键的问题：Parser 的不确定判断被静默当成事实，或一次无效构造污染后续推导。

### 7.2 工具接口

Geosym-World 工具应是领域纯能力，输入输出使用共享 schema，并支持在临时状态上执行：

- `construct`：执行 typed construction；
- `solve`：计算目标或局部事实闭包；
- `calculate`：精确表达式计算；
- `measure`：在明确坐标系/图像中测量；
- `inspect`：查询对象、邻接、可见区域；
- `verify`：验证 claim、construction 或 state invariant；
- `render`：渲染全局或局部 scene；
- `parse`：生成 hypotheses，不直接提交事实。

GeoClaw 的工具层只包装这些能力，增加：

- Agent action schema；
- 工具 allowlist；
- 调用预算和超时；
- 参数 grounding；
- public/private 信息投影；
- typed error；
- trajectory event。

不建议现阶段建立第三个 shared-code 仓库。共享契约由 Geosym-World 拥有，GeoClaw 通过依赖获得，避免再次形成三方同步问题。

### 7.3 Verifier Gate 的职责切分

一次 GeoClaw 动作建议按固定顺序处理：

1. **Parse**：模型输出能否解析为唯一 typed action；
2. **Schema Gate**：字段、类型、枚举和必填项是否合法；
3. **Policy Gate**：工具是否开放，动作是否允许，是否超过预算；
4. **Grounding Gate**：对象 ID 是否存在、可见且类型兼容；
5. **Tentative Execute**：在临时状态副本执行，不修改持久状态；
6. **Tool-Specific Gate**：工具自身的前置条件和结果约束；
7. **Geometry Gate**：退化、矛盾、不变量和事实一致性验证；
8. **Commit/Rollback**：全部通过才提交，否则持久状态保持不变；
9. **Privacy Projection**：只向模型返回可公开的 typed feedback；
10. **Trajectory Append**：记录 action、gate 结果、状态版本和审计证据。

## 8. Benchmark 和 Diagnosis 的边界

### 8.1 Geosym-World 负责

- 合成记录合法率、精确计数、重复率、覆盖率；
- 2D/3D primitive、construction、solver 和 verifier 正确性；
- Parser 的对象、关系、数量、target、grounding 和 state-level 指标；
- 渲染的标注完整性、遮挡、延长线、垂足、角标和表达式质量；
- 数据集切片、难度、分布、污染、lineage 和 schema 兼容性；
- 组件级错误归因：vision/text/fusion/grounding/kernel/solver/rendering。

### 8.2 GeoClaw 负责

- final answer accuracy 和 task success；
- action parse/schema/grounding/geometry acceptance rate；
- useful、invalid、rejected、recovered action；
- rollback 正确性和 replay 一致性；
- tool choice、调用次数、token、延迟和成本；
- 不同模型、controller、gate、反馈策略和预算的对比；
- 轨迹级错误归因和失败恢复分析。

任务数据可以由 Geosym-World 发布，Agent trajectory 和 Agent 实验结果应由 GeoClaw 管理。这样 Benchmark 数据定义与 Agent 策略评测不会互相污染。

## 10. 删除原则

用户要求删除过去测试、未开发完整、测试结果的代码和数据。建议把它落实为以下可验证规则，而不是按目录名全删。

### 10.1 可直接列入删除候选

- `__pycache__`、`.pyc`、`.pytest_cache`；
- 一次性 smoke/debug/replay 输出；
- 可以由配置和 seed 重建、且无论文或回归价值的生成图片和 JSONL；
- 空目录、失效入口、只引用已不存在模块的脚本；
- 已由权威实现替代、且 capability parity 已通过的源码副本；
- 无调用者、无测试、无文档契约、无独有能力的半成品模块；
- 重复 PDF、打包文件、临时日志和中间导出。
- 旧 `GeoClaw/paper/` 全目录；该项已由用户明确确认，不进入能力迁移范围。

### 10.2 必须迁移或归档后才能删除

- 旧 `scripts/tools` 中当前实现没有覆盖的图形、推导规则、着色或标注逻辑；
- 能复现历史论文数字的 frozen tasks、manifest 和必要结果；
- 用户修改但未提交的代码；
- 体现关键 bug 的最小 fixture；
- 当前 GeoClaw 的 rollback、privacy、budget 和 replay 契约测试；
- 当前 2D/3D、Parser、渲染和合成的有效回归测试。

### 10.3 关于“删除过去测试”

不建议删除所有旧测试后再重构。正确做法是：

1. 删除只验证旧目录结构、旧 CLI 文案或一次性实验的测试；
2. 把仍然正确的行为测试迁移成新 schema/API 的 contract 或 regression test；
3. 合并重复测试；
4. 在新实现通过后删除旧测试文件。

否则无法判断重构是“精简”还是“能力回退”。

## 11. 分阶段执行计划

### 阶段 0：冻结与盘点

不改代码，生成只读清单：

- 两个现有仓库的 HEAD、remote、branch、status 和 diff；
- 所有未跟踪文件和用户修改；
- 文件大小、checksum、Git 跟踪状态；
- Python import/call graph；
- 数据、输出、论文和实验产物清单；
- 现有能力 ledger：来源、目标模块、测试、处置方式。

产物：`inventory.json`、`capability_ledger.md`、`deletion_manifest.md`。

### 阶段 1：建立两个干净仓库骨架

- 创建工作区根 `Geosym-World/` 和 `GeoClaw/`；
- 设置独立 `pyproject.toml`、`src` layout、tests、docs 和 `AGENTS.md`；
- 在两个仓库内分别建立自有 `artifacts/` 目录和 ignore/manifest 规则；
- 建立统一 formatter/lint/test 配置，但不做无关全仓格式化；
- 确认本地 `conda activate geosym` 后都可 editable install；
- 建立数据和运行目录配置，不再硬编码 `/data/...` 或 `/dev/shm/...`。

### 阶段 2：先冻结共享 Geometry State Contract

- 定义稳定 ID、entity、relation、quantity、target；
- 分离 observation、hypothesis、admitted fact 和 certificate；
- 定义 provenance、visibility、confidence 和 state version；
- 定义 construction event 和 verification report；
- 定义 JSON 序列化、schema version 和兼容策略；
- 建立 round-trip、ID stability 和 contract tests。

这是后续所有迁移的前置条件。未冻结该契约前，不应同时大改 Parser、合成和 Agent。

### 阶段 3（首先开发）：迁移 Geosym-World 确定性内核

- 迁移 common schema、2D primitives、construction、solver 和 verifier；
- 保持现有行为，先不进行大规模算法重写；
- 用最小 fixture 覆盖相交、退化、精确值、事实依赖和 trace 执行；
- 迁移基础 3D primitive 和最小验证链，共享 contract 但隔离维度实现；
- 对 geosymsolid 和旧 3D 实现做能力对照，选唯一权威实现，不在此阶段承诺完整 3D 系统。

### 阶段 4（首先开发）：稳定渲染、合成、数据和 Parser v0

- 迁移统一 RenderScene、SVG/PNG 双输出和标注布局；
- 保留角标、垂足、延长线、点名冲突、根式/分式和阴影区域能力；
- 迁移模板、参数网格、增强、去重、精确计数和 manifest；
- 将数据集读写改为 adapter + registry + lineage；
- 大体积输出写到 `Geosym-World/artifacts/`，源码仓只保留小 fixture；
- 先迁移合成图、矢量图、干净标准图和结构化文本的 Parser v0；
- 建立 `synthetic record -> render -> parse -> compare` 的闭环 Benchmark；
- 分离组件指标、状态指标、答案指标和失败组件诊断。

### 阶段 5（首先开发）：重构 GeoClaw 确定性 Agent Runtime

- 把内层独立 GeoClaw 仓库提升到工作区根；
- 删除其复制的几何包，改为依赖 Geosym-World；
- 迁移并统一 model client、protocol、environment、gates、tools 和 trajectory；
- 把 persistent state 与 tentative transaction 明确分离；
- 统一 accepted/rejected event、rollback 和 replay；
- 保证 private certificate 不进入 model-visible payload；
- 建立 agent/tool/gate 的 contract tests；
- 只使用可信 formal task、public problem 和合成渲染图建立首期 Agent 基线；
- 将运行、trajectory、模型输出和评测写入 `GeoClaw/artifacts/`。

### 阶段 6（其次开发）：标准化真实数据 Parser 研究

- 从根 `geosym/` 继续迁移可复用的 vision/text/fusion/grounding 原型；
- 先选择版式相对统一的数据集，建立小规模人工对齐 gold set；
- 所有 Parser 输出进入 hypothesis 层，记录 confidence、provenance 和候选冲突；
- 分别评测 detection、OCR、relation、quantity、target、grounding 和 state consistency；
- 明确拒识和无法 grounding 的输出，不用静默兜底伪造完整状态；
- 去除硬编码路径、隐式缓存和运行时静默恢复；
- 只有标准化数据集指标稳定后，才扩展扫描、遮挡、低分辨率和开放版式。

此阶段是研究里程碑，不作为双仓重构完成的前置条件。

### 阶段 7（其次开发）：GeoClaw 不确定状态集成

- 让 Agent 读取多候选 Parser hypothesis 和证据来源；
- 增加 inspect、compare、request-evidence、admit/reject 等受控动作或等价协议；
- 由 gate 决定 hypothesis 是否可进入持久状态；
- 区分 Parser 错误、Agent 决策错误、工具执行错误和 verifier 拒绝；
- 建立 OCR、grounding、关系冲突和无效构造的恢复 Benchmark；
- 在首期 rollback、replay、privacy 和 formal-task 指标保持稳定的前提下评测真实题图。

### 阶段 8（其次开发）：高级 3D 与复杂任务

- 扩展高级 3D 构造、截面、投影、展开和 CAD 一致性；
- 扩展复杂合成 grammar、迭代构造、证明程序、区域和多步骤 target；
- 建立 3D rendering、Parser 和 Benchmark；
- Geosym-World 的 3D tools 稳定后，再接入 GeoClaw 3D Agent；
- 每项高级能力独立设 gate，不作为其他方向的隐式依赖。

### 阶段 9：分层能力对齐与验收

至少完成以下验收后才能删除旧实现：

- 2D 代表图形和构造的 exact-state 回归；
- 500 条合成任务的 exact-count、唯一性、目标完整性和结构审计；
- SVG/PNG scene 一致性及标注视觉抽检；
- 首期基础 3D 代表实体和最小数值验证；
- Parser v0 fixture 的对象、关系、数量、target 和 grounding 指标；
- GeoClaw 无效动作不改变持久状态；
- replay 后状态和轨迹 checksum 一致；
- public payload 无 private state、answer 或 oracle 泄漏；
- 至少一个真实 model adapter 完成离线协议测试和受控集成测试。

真实数据 Parser、高级 3D 和不确定状态 Agent 分别使用自己的研究 gate；未达到这些后期 gate 不等于基础重构失败，也不能对外宣称相关能力已经完成。

### 阶段 10：删除、归档和 Git 收口

- 根据最终 `deletion_manifest.md` 删除缓存、结果、重复实现和失效模块；
- 删除旧 `GeoClaw/paper/`，不迁移其源码或目录结构；
- 唯一但非活动的历史材料移入只读 `archive/`；
- 几何数据和生成结果移到 `Geosym-World/artifacts/`，Agent 运行和评测移到 `GeoClaw/artifacts/`，并分别补 manifest；
- 删除无效根 `.git`；
- 检查工作区只剩两个有效 Git 根；
- 在两个仓库分别提交职责单一的迁移 commit；
- 从全新 clone 执行安装、测试和最小生成/Agent replay 验证。

## 12. Git 历史策略建议

建议不要在当前脏工作树上直接“大清理后一次提交”。推荐策略是：

1. 把现有两个仓库按当前 HEAD 和未提交 diff 做只读快照；
2. 保留旧仓库或 bundle 作为历史证据；
3. Geosym-World 使用干净历史导入经过筛选的源码，不导入生成图片历史；
4. GeoClaw 尽量保留现有独立仓库历史，在明确 commit 中删除复制几何包并切换依赖；
5. 每一阶段独立 commit，不混入数据搬运、全仓格式化和无关文档修改；
6. 在新仓验证完成前，不删除旧仓和 archive。

这一策略比对当前历史直接做大规模 filter/rewrite 风险更低，也便于回看旧实验。是否需要保留 Geosym-World 原仓全部 Git 历史，应在执行前由用户确认。

## 13. 完成标准

重构完成不以“目录变少”为标准，也不要求在同一阶段解决开放世界真实 Parser、高级 3D 和所有 Agent 推理问题。基础重构以下列条件为准：

- 工作区只有两个活动 Git 仓库；
- 两个仓库都能在 `geosym` 环境中独立安装和测试；
- Geosym-World 不依赖 GeoClaw；
- GeoClaw 通过包依赖调用 Geosym-World，没有复制的几何源码；
- 合成、Parser、Benchmark 和 Agent 使用同一个 schema 和 ID 体系；
- Parser hypothesis 与 admitted fact 明确分离；
- 无效 Agent 动作可证明不会污染持久状态；
- 所有数据和实验结果有 manifest、seed、配置和各自仓库内的产物路径；
- Geosym-World 与 GeoClaw 的 artifacts 物理分开、责任分开、清理策略分开；
- 源码仓不跟踪缓存、大规模生成图片和运行结果；
- 所有绝对路径改为显式配置；
- 新 Agent 进入任一仓库时能自动读到对应 `AGENTS.md`；
- Git status 在测试和最小运行后保持干净；
- 删除清单中的每一项都有“已迁移、已归档、可重建或确认无价值”的依据。

## 14. 主要风险

1. **过早删除测试导致能力回退不可见**：应先迁移有效契约测试。
2. **两套几何实现继续漂移**：必须尽早冻结共享 contract，并让 GeoClaw 单向依赖。
3. **Parser 假设污染事实状态**：schema 必须在类型层强制区分 hypothesis 与 fact。
4. **2D/3D 强行统一导致抽象膨胀**：共享契约，隔离算法实现。
5. **数据移动后实验不可复现**：先生成 checksum、manifest 和来源记录。
